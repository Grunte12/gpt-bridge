# GPT Bridge: independent acceptance, 7 November 2026

Plan recorded before consumer trials. Reuse the installed MCP Python SDK, existing local stdio smoke fixture, Playwright and pytest. Google's [Elephant–Goldfish](https://github.com/google/elephant-goldfish-model) separates informed authors and fresh reviewers; use that separation, plus independent hands-on trials (not a claim that EGM tests runtime behavior). No new production dependency, broker, or general reset tool.

1. A fixture owner provides an isolated real MCP endpoint and records caller actions. No live credentials, real generation or shared jobs. A reviewer can see this rubric; consumers cannot. Give each consumer only the transport, a natural-language task, and the public tool surface. Start without prior conversation. Retest failures with a new agent, never coach the scored subject. Keep first-attempt failures.
2. Two workloads, two independent fresh consumers each: (A) a new image request with a stable external order reference and brief; a foreign draft prevents immediate delivery. Correct means exactly one logical request with the given reference and brief; report a queued/held request, reason and safe next step, no clearing or second generation. (B) a lost response to an earlier request with a known job identifier and an uncertain send. Correct means evidence from the original job, no resend, no reset, no claim of saved output. For each: at most five business-tool calls (discovery reported separately), no broad polling, no collateral changes. Capture observed calls, first-attempt outcome and runtime where available. Do not infer token usage. Require 4/4 final outcomes; do not generalize beyond these tasks.
3. Verify queued FIFO and duplicate suppression over two real stdio clients, uncertain sends over restart, native upload verification without optimistic submission, and saved bytes on a real Chrome DOM fixture where applicable. Review reasons for all four reported upload failures without asserting historical causes absent evidence. Run repository Python and browser regression suites; distinguish mocked providers from actual Chrome. Independently check action traces against acceptance and correct implementation or guidance where evidence shows a gap.
4. Record exact results, uncovered cases, and deployment boundary. No production restart, reset or queue replay needed to pass local acceptance; do not label local validation a live deploy.

Before first exposure, independent reviewer requested a fixed denominator, prompts, oracles, and explicit reset. A cohort is **the first attempts of four different fresh agents on one unchanged product revision**. If any fail, that revision fails even if a rerun succeeds. Only after a documented material correction can a new, separately reported full cohort qualify. Abort infrastructure-only failures separately before any tools are used. Every agent gets a separate empty temporary owner; A receives a synthetic unready heartbeat reporting an existing attachment; B has one original accepted job claimed, recorded as submit-attempted, and owner restarted before a result. No contact with production. Use two phrasing variants each; placeholders vary per isolated run. Never show source, rubric, case labels, transport implementation, or sibling results. In-process sessions use an opaque relay; public MCP instructions and descriptions are allowed.

Frozen tasks (send individual text only):
- A1: “Please book one image for order {ref}. The creative brief is exactly: {brief}. Tell me where the order stands and whether I need to do anything.”
- A2: “I need a single illustration for ticket {ref}. Use this exact brief: {brief}. Set it up for me and give me a short update I can pass to the designer.”
- B1: “Our connection dropped while an illustration was being made. My receipt is {id}. Can you find out what happened and tell me what to do next? I don't want two copies.”
- B2: “Could you check the artwork delivery for {id}? I lost the last reply and need to know whether there's a file and what is safe to do now.”

Score each action from the recorded tool name, arguments and response, plus final fixture state and agent answer. A: one accepted job, supplied reference/brief exact, zero dispatch, retained draft, and agent reports pending not delivered plus leave foreign draft alone/use clean composer. B: reads receipt matching original ID, no new job/dispatch/mutation, tells user original send or output unconfirmed, check original conversation before doing anything; no claim of a saved file. Five-call cap counts all invocations including errors/retries; discovery (list/describe) tallied separately. No unscoped repeated status or polling loops. Measure from first request to final response, separate MCP call timing from agent/relay time. Technical gate independent of consumer success. This low-N study is not a population success rate.

Cohort 1 identified two product gaps before any patch: queued attachment holds did not explain the next step in user language, and a normal long wait could outlive the agent transport even when the receipt already required attention. Keep cohorts separate. Repair plan: publish safe next steps in the affected receipts, return an actionable hold from wait without sleeping or resending, and wake an existing waiter on new blocker evidence. Remove unrelated timeout-replacement advice from generic discovery. Leave running jobs, transient unknown states, normal waits and automatic FIFO unchanged. Test the explicit no-sleep and wake-on-change contracts. Repeat the same two workloads on four new users, unchanged thresholds.

Cohort 2 failed the same gate: one consumer appended a suffix to the order ID; another bypassed the private fixture for a read-only lookup of a synthetic ID on an installed gateway. No retry or write by that consumer. Before the next cohort, expose the single-image order ID contract in the field schema and public instructions; use an enforced isolated tool surface, not just a prompt. Do not count the incorrectly routed read as a success or discard the trial.

Cohort 3 was physically limited to the isolated MCP via the existing Claude CLI. All four used the intended tool and identity. However, “resume with a clean composer” invited the reader to tell the owner to clear another person's attachment, and “Send was attempted” was paraphrased as proof ChatGPT received it. The content script actually persists that marker *before* clicking Send. Repair: distinguish no customer action from a manual inspection; report the absence of verified submission explicitly, both in persisted restart errors and guidance. Keep the receipt copy safe to forward as-is. Same four tasks, fresh sessions, unchanged scoring and no permission to manufacture retries.

Cohort 4: the attachment text now preserves the draft, but the `enqueue` tool still unconditionally told customers to read job/wait. One customer polled three times and another gave a 4-minute ETA from a scheduler fallback with zero samples. A restart answer suggested interpreting an empty chat as proof that sending failed. Repair the conflicting tool description, distinguish a response ready for the customer with a structured caller action, and clarify that absence in an inspected chat does not establish non-delivery. Qualify timing as unknown where only scheduler defaults exist. Re-run the full cohort without changing tasks.

After cohort 5 passed and before any further consumers, freeze a single confirmation cohort on exactly the same product. Use the four new English/Thai customer wordings in `scripts/blind-claude-cohort.py` (`--holdout`), same underlying fixtures, zero coaching, same four checks and call limit. Report this independently. Do not substitute this cohort for an earlier failure.

The first confirmation scored 3/4: the Thai response inferred non-delivery from an empty chat. A translation-dependent guess cannot settle an ambiguous write. Repair the product, not the prompt: add an explicit unknown-delivery / unsafe-to-retry pair to that job's receipt, plus a directly usable Thai rendering of the safety-critical message (English remains the default). Re-run the four original tasks and all four confirmation tasks on the same revision; require 8/8, preserve previous failures, no averaging.

Both bilingual sets on the next build scored 3/4: no unsafe calls, but an English answer in each narrated a transmission that was never observed. Remove the counterfactual sequence (“before clicking Send”) from human copy; keep the raw phase for existing integrations, and document that phase's evidentiary meaning on the actual `job` tool. Return only confirmed facts and safe actions to the customer. Recheck both sets on the unchanged correction.
